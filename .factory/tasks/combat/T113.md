# T113 — Queue attacks against the combatant registry contract

## Description

T085's open finding (checklist C2): `EngagementQueue` takes the concrete `CombatantRoster` because
it needed `byId`. Architect change-04 (`ports-combatant_registry`) added `Combatant? byId(EntityId)`
to the contract, so the use case now depends on `CombatantRegistry`. The named parameter keeps its
name, `roster`, so every caller compiles unchanged. This is step 1 of change-04's note; the move of
the roster to `infrastructure/` follows in T143–T145 (planner wave-05 `roster-move-expand-contract`).

## Preconditions

- On `main`, `CombatantRegistry` declares `register`, `unregister`, `near`, `positionOf` and `byId`
  (architect change-04).
- On `main`, `EngagementQueue({required CombatantRoster roster, …})` as T085 integrated it.

## Constraints

- Behaviour unchanged: the same calls on the registry, in the same order.
- `engagement_queue.dart` and its test no longer import `combatant_roster.dart`.
- The test file stubs a `MockCombatantRegistry` (`near`, `byId`) instead of a real roster
  (testing §4.1); each existing test keeps its name and its assertion.
