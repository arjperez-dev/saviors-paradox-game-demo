# T084 — Publish what an exchange resolved

- **Date:** 2026-10-17
- **Outcome:** Built `ReportExchange`, the application use case that turns combat's domain events
  (`EngagementEvent`, `FlightEvent`) into the integration events `HitLanded`, `AttackBlocked`,
  `CounterTriggered`, `ProjectileReflected`, `HitstopStarted` and `SoundEffectCued`, and calls
  `StatusEffectControl.apply` for afflictions, in the order each criterion states. All 10 criteria
  pass; `verify-task` reports `implemented`.
- **Decisions:** for the two `StrikeBlocked` tests whose `Assertion` does not fix a hitstop value
  (the affliction and the slow tests, both an ice shield), used `Seconds(0.05)` — `hit-feedback.md`
  §2's "blocked, ice shield" row — rather than the sacred-only "perfect block, melee, sacred shield"
  row's `0.09`, since that table notes a perfect block with the ice or fire shield draws as their
  plain block.
- **Deviations:** the tester ran and reported two gaps, both closed in this task's own files:
  - **C7** (`coding-standards.md` §6 rule 6, cited reference, "no boolean parameters that switch
    behaviour; two methods, or an enum"): the task's literal `Implementation` had
    `_cueBlock(ShieldId shield, Vec2 at, {required bool isPerfect})` gating an extra cue by a
    boolean. Since the reference wins over a literal `Implementation` it contradicts, split it into
    `_cueBlock(shield, at)` and `_cuePerfectBlock(shield, at)` (the latter calling the former then
    cueing `CombatSounds.perfectBlock`), with both call sites choosing between them with an `if`
    instead of passing a flag.
  - **T5** (`testing.md` §3, cited reference, "a value a reference fixes is asserted with that value
    and the reference named in a comment"): added a `// hit-feedback.md §2: …` comment to every
    hitstop literal in the test file, naming the table row it comes from.
- **Evidence:** files touched, both listed in the task's `files`: `lib/features/combat/application/
  report_exchange.dart` (new) and `test/features/combat/application/report_exchange_test.dart`
  (new). The `Implementation` block was otherwise used as written; `GameEvent` subclasses
  (`HitLanded`, `AttackBlocked`, etc.) have no `==`/`hashCode` override, so tests capture
  `events.publish` calls into an ordered `List<GameEvent>` via `thenAnswer` and assert each event's
  fields and the list's order and length, rather than comparing whole events by equality.
