# T106 — Test a zone from its seed to its collisions through the loop

- **Date:** 2026-10-17
- **Outcome:** Added `test/integration/dungeon_zone_test.dart`: one `group` building a real
  `GameLoop` over a real `EventQueue` and `StepClock`, stepping `StepZone`, against a real
  `InMemoryZoneRepository`, `SeededZoneGenerator(kits: [SuspendedSanctuaryKit()])`,
  `ZoneCollisionWorld`, `BossRoomDoors` and `ZoneAltars` — nothing mocked. Five tests, one per
  criterion: a seed becoming a zone the loop publishes as one `ZoneEntered` (zone 1,
  `suspendedSanctuary`) with 36–44 rooms and 13 on the main path; a body dropped above the start
  landing on its floor through `ZoneCollisionWorld.sweep`; the first of seeds 1–10 whose zone
  holds drifting platforms moving at least one box over 60 loop frames; `sealBossRoom()` then
  `doors.unseal()` publishing one `SoundEffectCued` with sound `BossRoomDoors.opened` through one
  frame, and `stepZone.state.isBossRoomSealed` turning false; and `altars.returnTo(...)` with an
  `AltarShield(shield: ShieldId.ice)` showing as `stepZone.state.altars.first.item`.
- **Decisions:** The acceptance table names the test bodies' assertions but not their arrangement
  in full; where it left room I followed the existing precedent in `test/features/dungeon/`'s
  unit tests (`boss_room_doors_test.dart`, `step_zone_test.dart`) for shape: reaching the loaded
  `Zone` through `InMemoryZoneRepository.load()` to call `sealBossRoom()` directly, and searching
  seeds 1–10 for the first zone with platforms, the same way `step_zone_test.dart` does. Each test
  calls `generator.generate(...)` itself rather than sharing one generated zone across tests, to
  keep them independent (`testing.md` §3); the "doors" test advances one frame right after
  generating, before sealing, so the `ZoneEntered` already delivered does not mix into the
  `published` list the criterion checks against the door's `SoundEffectCued`.
- **Deviations:** none.
- **Evidence:** No `Implementation` section applied — this is a test-only task. Files touched:
  `test/integration/dungeon_zone_test.dart` (new, as listed in `files`), nothing else. The tester
  ran after the suite was green (`flutter test`: 586 passed) and `dart format` / `flutter analyze
  --fatal-infos` clean; it found two checklist items to close, both fixed: G6 (`coding-standards.md`
  §9.2), a comment now names `layout.md §B.1` by the 36–44/13 room-count assertions; C4
  (`coding-standards.md` §3, 20-line limit), the platforms test's body was extracted into two
  top-level helpers, `_firstSeededPlatforms` and `_anyBoxChanged`. It also raised, as an
  ambiguity rather than a finding, whether `zones.load()!.sealBossRoom()` reaches into the
  dungeon feature's private code against `testing.md` §7's "never reach into a feature's private
  code": I read this as licensed rather than contradictory, since `Zone` is the aggregate the
  task's own `InMemoryZoneRepository` (one of the real, unmocked collaborators the task's
  Description names) returns, the task's own `Assertion` column directs this exact call, and the
  same direct call on a loaded `Zone` is the established pattern in
  `boss_room_doors_test.dart:47`; §7's "private code" reads as code outside a feature's public
  aggregates and ports, not as forbidding a feature's own integration test from using its own
  aggregate root the way its application layer already does.
