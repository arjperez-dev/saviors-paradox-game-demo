# T093 — Check a zone layout can be played

- **Date:** 2026-10-17
- **Outcome:** Added `ZoneValidator` (domain/policy, specification) — checks a `ZoneLayout` has
  the fewest rooms, the fewest dead ends, every room reachable from the start, and the boss
  reachable from the start through main-path rooms alone — with its 5 acceptance-criteria tests,
  built from `SuspendedSanctuaryKit`'s templates per the acceptance text.
- **Decisions:** The playable-layout fixture builds its five `PlacedRoom`s from
  `SuspendedSanctuaryKit().templatesOf(kind).first` rather than ad hoc templates, matching
  "builds a small `ZoneLayout` by hand from the sanctuary's templates" in the Acceptance criteria
  section.
- **Deviations:** none to the Implementation — it was put in verbatim and compiled and passed
  against T091's `ZoneLayout`/`PlacedRoom` and T090's `RoomKind` as they stand on this branch. The
  tester found no gap in a criterion of this task and no checklist item the code fails. Open
  finding (not a checklist fail, a note for the architect/planner): `architecture.md` §4's
  "Policy / specification" row says that building block is "composable (`and`, `or`, `not`)",
  which `ZoneValidator` does not have — but `design-patterns.md` §14 says a pattern with a single
  implementation and no second case in sight stays a plain class until the second case arrives,
  and this is the first specification in the codebase (confirmed by a grep of `domain/` for
  `isSatisfiedBy`). Read together, the two cited references resolve in favour of the task's own
  `Implementation`/`Interfaces` exactly as given, so no code change followed from this; it is left
  here for whoever adds the second specification to weigh.
- **Evidence:** No adaptation was needed; the Implementation compiled and passed as written.
  Files touched: `lib/features/dungeon/domain/zone_validator.dart` (new),
  `test/features/dungeon/domain/zone_validator_test.dart` (new) — both listed in the task's
  `files`.
