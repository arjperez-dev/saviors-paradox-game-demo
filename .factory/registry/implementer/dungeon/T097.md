# T097 — Guard a generated zone behind its root

- **Date:** 2026-10-17
- **Outcome:** Added `Zone`, the aggregate root of a generated zone (domain, aggregate), assembled
  from a layout via a factory `Zone.of`; its entities `Room`, `Altar`, `DriftingPlatform`
  (library-private, part of `zone.dart`); the assembly helpers `_Assembly`/`_Parts`
  (`zone_assembly.dart`); the value objects `RoomView`, `AltarView`, `SpiritPlace`; and the domain
  events `BossRoomSealed`, `BossRoomUnsealed`, `ItemTakenFromAltar`, `ItemReturnedToAltar`
  (`zone_event.dart`). All 20 acceptance-criteria tests pass, plus the whole suite (542 tests) and
  `flutter analyze --fatal-infos` clean.
- **Decisions:** none the task file left open; the acceptance criteria fixed the seed-search and
  the "an altar"/"its position" shorthand exactly, so the tests follow them literally (a helper
  that finds the first 1–3 seeds whose layout both builds and passes
  `ZoneValidator(fewestRooms: 36, fewestDeadEnds: 9)`, reused for the two tests — platforms moving,
  and a box meeting a platform — that need a layout with at least one drifting platform).
- **Deviations:**
  - The tester (run after the suite was green) found the literal `Implementation` violated
    checklist **C4** (no class over 200 lines): `Zone`'s body, as given, spans 205 lines. Fixed by
    extracting the altar bookkeeping (`giftOn`, the nearest-altar search, `takeFrom`/`returnTo` and
    the cached `AltarView` list) into a new private class `_AltarBook`, in a new file
    `lib/features/dungeon/domain/altar_book.dart` (`part of 'zone.dart'`, not in the task's `files`,
    but inside `lib/features/dungeon/domain/`, so inside the module's root — file gradient,
    `TASK_FILE_SPEC.md` §3.2). `Zone` now delegates to it and bumps `_revision` itself on a non-null
    result; `Zone`'s body is 170 lines. Behaviour is unchanged — same public methods, same returned
    events, same revision bumps — and every test (including the tester's own prior pass) still
    passes. The two `prefer_initializing_formals` info-lints this also surfaced on `Altar._` and
    `DriftingPlatform._` (from the literal `id`/`room`/`position` parameters shadowing the `_id`/
    `_room`/`_position` fields) were fixed the same way: `required this._id` etc., keeping the
    named-argument labels at the call sites in `zone_assembly.dart` as `id:`/`room:`/`position:`
    (Dart derives the public label from the field name without its leading underscore; this
    matches the existing pattern in `lib/core/localization/application/translator.dart`).
  - The tester also reported checklist **A13** ("an input it cannot build from is a sealed result,
    not an exception") against `_Assembly.roomWhere`/`spotIn` (`zone_assembly.dart`), which —
    exactly as the task file's `Implementation` gives it, verbatim — `throw StateError(...)` when a
    layout lacks a room or spot a zone needs. Reviewed, not changed: the task's `Interfaces` row
    fixes `Zone.of`'s signature as a plain (non-nullable, non-`Result`) factory, so honouring A13
    literally would mean changing that fixed signature (rule 15 lets me honour it or stop, not
    silently change it). The actual failure mode — a `ZoneLayout` missing its start, boss, way
    down, antechamber or lore dead end — cannot occur with a layout `ZoneValidator` has passed (its
    own `_bossOnMainPath`/`_everyRoomReached` checks require these rooms to exist), which is this
    task's own stated precondition ("the tests take their layout from T092's `ZoneBuilder` and
    T093's `ZoneValidator`"). That makes it a broken invariant on an already-validated collaborator
    — coding-standards.md §7's "impossible state" row, correctly a `StateError`, never a sealed
    result — not the "expected failure" row A13's clause describes. Left as the task file gives it;
    flagging here rather than silently dropping the tester's finding, in case the operator reads
    A13 more broadly than I have.
  - No other deviation: every other file was put in verbatim from the `Implementation` and compiled
    and passed as written against `BiomeKit`, `ZoneGeometry`, `Sweep`, `Contact`, `DriftPath`,
    `PlacedRoom`, `ZoneIds`, `ZoneLayout`, `ZoneGrid`, `AltarGift` and the kernel contracts as they
    stand on this branch.

  Every other file in `files` — `room.dart`, `altar.dart`, `drifting_platform.dart`,
  `room_view.dart`, `altar_view.dart`, `spirit_place.dart`, `zone_event.dart`,

  `spirit_place_test.dart` — was written as the task gives it, with the test bodies written against
