# T028 — Trace the kit's strokes into a reusable path

- **Date:** 2026-10-14
- **Outcome:** all 5 criteria have a test under its exact `Test name`; `flutter test test/core/rendering/presentation/stroke_paths_test.dart` — 5/5 pass; `flutter analyze --fatal-infos` on both files is clean. `stroke_paths.dart` is verbatim the task's `Implementation` code block, so the `Interfaces` table's four signatures match the code exactly.
- **Decisions:** no manual test written — the task file has no `Manual check`.
- **Deviations:** none at the literal-assertion level — each test asserts exactly the bound, containment or value its `Assertion` states (line width ≈100±1; circle contains its centre, left in [25,33]; triangle contains (8,2); hatching bounds top=-2/bottom=52 exactly; the replace test's exact `Rect.fromLTRB(0,0,10,10)`).
- **Evidence:**

  **Covered.** Criterion 1 (line): `traceLine` with a horizontal `QuadraticPass` gives `width` within 1 of 100 — matches. Criterion 2 (closed curve): 16 points of a radius-20 circle at (50,50), `contains` and `left` both checked — matches. Criterion 3 (polygon): the triangle (0,0),(10,0),(10,10) contains (8,2) — matches. Criterion 4 (hatching): `Hatching.generate` with a fixed `Seed(1)`, `traceHatching` gives exact top/bottom bounds — matches, and the exactness is legitimate: `Hatching`'s y-endpoints (`bottomRight.y + 2`, `topLeft.y - 2`) are never jittered, only x is, so asserting them exactly (no `closeTo`) is correct per `testing.md` §3's "exact where the reference is exact," even though `strokes.md` doesn't fix this specific numeral itself. Criterion 5 (replace): tracing a line then a polygon into the same `Path` gives the polygon's bounds alone — matches, and demonstrates the module's whole point (a reused `Path`, no allocation, architecture §6.1).

  **Not reached — a real gap, confirmed by mutation.** The test named "traces every stroke of the hatching" does not actually prove every stroke is traced. Every individual `HatchLine` `Hatching.generate` produces has the *same* fixed y-span (`topLeft.y - 2` to `bottomRight.y + 2`, independent of `x`/jitter/slope), so the test's bounds-only assertion (`bounds.top == -2`, `bounds.bottom == 52`) is satisfied by tracing a single line exactly as well as by tracing all of them. I verified this directly: temporarily changing `traceHatching`'s loop condition from `i < lines.length` to `i < 1` (drop every line but the first) in `lib/core/rendering/presentation/stroke_paths.dart`, the whole suite — including this test — still passes 5/5; reverted after confirming. A regression that silently dropped most of the hatching would go undetected. What's missing: an assertion that distinguishes "all lines traced" from "one line traced" — e.g. also check `bounds.left`/`bounds.right` (which do vary with the number and position of lines, given the `rise` and `gap`), or assert that two interior points belonging to two different lines (not just one) are each near the path, or count the path's contours/segments against `hatching.lines.length` (e.g. via `path.computeMetrics().length`).

  **Narrower, lower-severity gap.** The "replaces what the reused path held" criterion/test exercises only the `traceLine` → `tracePolygon` transition. `traceClosedCurve` and `traceHatching` call `path.reset()` identically, so the reset behaviour is uniform in the code, but no test exercises reset starting from — or into — those two methods specifically (e.g. `traceHatching` after `traceClosedCurve`, or `traceClosedCurve` after `traceHatching`). Given the four methods share the same one-line reset idiom, this is a minor, not a functional, gap.

  **Inherent, not actionable.** No test can distinguish whether `tracePolygon`/`traceClosedCurve` actually call `.close()` from one that doesn't: `dart:ui`'s `Path.contains` fills (and so implicitly closes) any subpath regardless, so the containment assertions criteria 2 and 3 use would pass either way. Noting this so it isn't mistaken for an oversight — it is a limit of what a non-golden-image unit test can observe here, consistent with `testing.md` §5's "pure functions first... geometry and choices, not pixels."
