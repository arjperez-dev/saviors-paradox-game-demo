- **Evidence:**

  **Covered, matching the `Assertion` and the cited references.** Criterion 1 ("fades a puff from 0.85 to nothing"): `puffAlpha(0)==0.85`, `puffAlpha(1)==0`, `puffAlpha(0.5)` within `1e-9` of 0.425 — matches, and the formula `(1-progress)*0.85` and the constant `0.85` match the sandbox's ink particle (`sandbox.html:1623`, `ctx.globalAlpha = (1-u)*.85`). Criterion 2 ("draws the body once a frame while it dissolves"): `paintBody` on a real `Canvas(PictureRecorder())` with a counting `drawBody` callback gives `calls==1` — matches. Criterion 3 ("paints the puffs of a dissolve in flight"): a picture recorded before any `dissolve.step` call is smaller than one recorded after 40 steps of `Seconds(1/60)` (~0.667s elapsed). I checked this premise against `InkHole`'s seeded `opensAt` (`ink-smoke.md` §1: holes open between 0.12s and 0.82s) and `InkDissolve._launchIfOpen`: at `elapsed==0` no hole has opened, so "before" is genuinely empty of puffs, and by 0.667s several have launched, so "after" is genuinely larger — the test's premise is sound, not just incidentally true for the fixed seed `6600`. Criterion 4 ("leaves the canvas as it found it"): after stepping 40 times (so `paintBody`'s `_holes` dstOut branch and at least one `_puff` branch in `paintPuffs` both execute) and calling both methods on one canvas, `getSaveCount()` equals its pre-call value. I traced the save/restore pairing in `_puff` by hand against `Pencil.clipToCurve` (which itself does an unpaired internal `canvas.save()` the caller must restore): `_puff` does `save()` → translate/scale → `fillCurve` → `clipToCurve` (a second, nested `save()`) → `hatch` → `restore()` (undoes the clip's save only, the translate/scale survives since it was applied before that save) → `line` (drawn still inside the outer transform, width-compensated by `1/scale`) → `restore()` (undoes the outer `save()`) — two saves, two restores, correctly balanced; `paintBody`'s `saveLayer()`/`restore()` is likewise one matched pair. The test's premise holds for the real implementation, not only by coincidence.

  **Not reached — the task's `Constraints` line has no automated test.** "`paintPuffs` allocates nothing per puff beyond the colours it computes" is not one of the four acceptance criteria, so no test asserts it; I verified it only by reading `_puff` (no `Offset` or other object is constructed beyond the `Color`s `_ink`/`withValues` produce; `_path`/`_paint` are the pre-existing reused fields on `Pencil`). This also bears on checklist A10 ("nothing in the per-frame path of a hot loop allocates") — satisfied by inspection, not proven by any test. A regression that added a per-puff allocation (e.g. a new `Offset`, a new `List`) would pass the whole suite undetected.

  **Not reached — `_holes`' erase and the body's own fade-out are exercised but never independently asserted.** Criterion 4's test calls `paintBody` after 40 steps, so the `radius > 0` branch inside `_holes` (erasing a circle with `BlendMode.dstOut` at `feet + hole.centre`) does run, and so does the `_paint.blendMode = BlendMode.dstOut` / reset back to `BlendMode.srcOver` afterward — but nothing checks that a hole is erased at the right centre/radius, or that the blend mode is restored to `srcOver` for the next frame's draw (only the unrelated `getSaveCount()` is checked afterward). Separately, `bodyAlpha < 1` (the body fading out, `elapsed` past `fadeStart==1s`) and `inkAlpha`'s own 0→0.2s ramp are never driven to a state where `paintBody`'s `_layer.color` alpha is itself asserted — no test reads back the colours a recorded `Picture` actually contains at any point. This is implied by `ink-smoke.md` §1 ("the body is gone" by ≈1.4s) but is not one of this task's four stated criteria, so it is a gap against the feature, not against this task's own acceptance table.

  **A weaker point already implied by the `Assertion`'s own wording, same limit as T028/T029's registry entries noted.** Criterion 3's assertion is byte-count-only, so it is satisfied whether a puff's blob, hatching and wisp are drawn with the right alphas/colours or the wrong ones, and whether `puff.growth`'s scale (`1 + 1.3*progress`) is applied correctly to `canvas.scale(scale)`. This is what the criterion literally asks for and matches the project's "no golden images" rule (`testing.md` §5, §8), but on its own it cannot distinguish a correct draw from a degenerate one that still draws *something* larger.
