- **Deviations:** none in the stated criteria. One branch of the `Implementation` no test enters: `returnTo` calls `_zones.save(zone)` unconditionally after `zone.returnTo(altar, readGift(item))`, whether or not the root actually laid the gift (the root's `give` returns `null`, and the zone is unchanged, when the altar already holds one or is unknown). A related input the criteria do not try: `returnTo` on an altar id the zone does not have at all (`Zone.returnTo` → `_AltarBook.give` → `null` the same way as "holds one already") — no test exercises an unknown-altar id, though the task's own criteria never ask for one.
- **Evidence:** Covered — "returns an item to its empty altar": with the repository mock returning the `Seed(1)` zone, `returnTo(altar, AltarScroll(scroll: health))` leaves `zone.giftOn(altar)` as `ScrollGift(health)` (`05-items/items.md` I4, named in the test's comment) and `zones.save(zone)` is called once. "with no zone nothing happens": `load()` returning `null` short-circuits `returnTo` — `zones.save` is never called. Not covered: `zones.save`'s call count on the no-op (refused-return) branch, and an unknown-altar id — both low-severity gaps, not violations of a stated criterion or a checklist item.
